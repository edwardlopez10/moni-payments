# AWS Secrets Manager Credential Storage

## Overview
<!-- @section:overview -->
An organization in Moniveo Payments can hold one or many payment accounts. Each account represents
the organization's relationship with a single payment provider such as N1CO, and exactly one is the
default. Every account needs provider credentials (client id, secret, webhook signing secret, and
so on). This spec moves those credentials out of the service's reach at rest.

The database stores only a service-generated reference. The values live in AWS Secrets Manager,
encrypted with a key dedicated to the running environment. The service writes and reads them
through a storage-agnostic abstraction, so only one module knows the backing store exists.

Security is the overriding concern:
- Credentials are write-only through the API. No endpoint, in any environment, ever returns a
  secret value.
- Staging and production are isolated by AWS policy and encryption keys, not just by application
  code.
- Every credential operation and account lifecycle change is audited and attributable.
- Logs, errors, and events are redacted by default.
- Credentials can be rotated without downtime.

A secret-store outage is treated as a configuration availability problem. It is not a payment
outcome, so no payment is marked failed because credentials were temporarily unreachable.

Success means:
- A staging deployment provably cannot read production credentials.
- Credential values appear in no API response, log line, or event.
- Every payment account follows the defined lifecycle.
- A secret-store outage surfaces as a retryable `PROVIDER_CONFIGURATION_UNAVAILABLE` error with no
  side effects.

Key considerations:
- **Decision**: a single AWS account for now, with staging and production separated by secret
  namespace, a dedicated runtime identity, and a customer-managed encryption key per environment.
  Separate AWS accounts remain the upgrade path.
- **Decision**: the runtime authenticates with IAM access keys, because Railway cannot attach AWS
  roles. Each environment has its own exclusive, least-privilege IAM user or role. These keys are
  the one bootstrap secret held outside the store, so they carry the highest residual risk.
- **Decision**: credential values are cached in process memory for at most 60 seconds.
- **Assumption**: local development and CI use a non-cloud implementation of the same abstraction
  and never need AWS credentials. Production refuses to run with it.
- **Non-goal**: automated rotation performed by AWS (Lambda rotation). Payment-provider credentials
  are issued by the provider, so rotation here means replacing them safely.
- **Non-goal**: a real N1CO adapter, cross-region replication, and private networking (VPC
  endpoints are unavailable on Railway).

## Requirements
<!-- @section:requirements -->
- (R-001) **Multiple accounts, one default.**
  - An organization can have one or many payment accounts, each tied to exactly one payment
    provider.
  - At most one account is the organization's default at any time.
  - Changing the default is atomic: there is never a moment with two defaults.
- (R-002) **References only in the database.**
  - Provider credentials are never persisted in the service's database, in any column, JSON field,
    audit record, or event.
  - Each payment account stores only a reference to where its credentials are held.
  - The reference is generated by the service from the environment, organization, and account
    identity, and is never accepted from a caller.
  - A reference outside the running environment's namespace is rejected.
- (R-003) **Storage-agnostic abstraction.**
  - All credential access goes through a single abstraction offering exactly four operations by
    reference: store, retrieve, delete, and check existence.
  - No other part of the service knows which backing store is in use.
  - Credential payloads are validated against the provider's expected credential shape when
    written and when read.
  - A malformed or incomplete payload fails closed and is never passed to a provider.
- (R-004) **Credentials are write-only.**
  - Credentials can be submitted while configuring a payment account and are written directly to
    the secret store.
  - No API endpoint, including development-only and administrative routes in every environment,
    ever returns a credential value.
  - Callers can see only non-sensitive metadata: which credential fields are set, when they were
    last written, and whether they are present.
- (R-005) **Account lifecycle.**
  - Allowed transitions:
    - `NOT_CONFIGURED` → `ONBOARDING` → `PENDING_VERIFICATION` → `ACTIVE`
    - `ACTIVE` → `SUSPENDED` or `DISABLED`
    - `SUSPENDED` → `ACTIVE` or `DISABLED`
    - `PENDING_VERIFICATION` → `REJECTED`
  - `DISABLED` and `REJECTED` are terminal.
  - Any other transition is refused with an explicit error.
  - An account cannot enter `PENDING_VERIFICATION` unless its credentials exist in the secret store
    and pass validation.
  - When an account enters a terminal state, its credentials are scheduled for deletion with a
    recovery window, never deleted immediately.
- (R-006) **Only active accounts transact.**
  - Only `ACTIVE` accounts can be used to process payments, refunds, or other provider operations.
  - If the requested or default account is not `ACTIVE`, the request is refused with an explicit
    error. The service never silently falls back to a different account.
- (R-007) **Environment isolation.**
  - Staging and production credentials are fully isolated. A deployment in one environment can
    neither read, write, delete, nor decrypt credentials belonging to the other.
  - Isolation is enforced by the secret store's own access and encryption controls: a separate
    namespace, runtime identity, and encryption key per environment. It is not enforced by
    application logic alone.
  - It is proven by an automated or checklist-driven negative test: the staging identity is denied
    access to production credentials.
- (R-008) **Least privilege.**
  - Each environment's runtime identity is exclusive to that environment and grants only the
    operations needed to store, retrieve, delete, and check existence within its own namespace.
  - It cannot list secrets, batch-read secrets, alter access policies, change tags, replicate,
    restore, or delete immediately.
  - No human or CI identity holds standing permission to read production credential values.
  - Redaction moved to R-010; attribution moved to R-011.
- (R-009) **Migration.**
  - Existing payment accounts keep processing payments through the migration.
  - Current statuses are mapped to the new lifecycle.
  - Current credential references are moved into the secret store under service-generated
    references.
  - After migration, production accepts no environment-variable-based references.
- (R-010) **Logging and redaction.**
  - Credential values and credential-bearing fields are redacted by default across logs, error
    messages, API responses, events, and traces.
  - Error details from the secret store are never forwarded verbatim to callers.
  - Automated tests fail if a known credential value appears in captured log output, response
    bodies, or emitted events.
- (R-011) **Audit and traceability.**
  - An audit record is produced for every credential write, rotation, deletion, existence check,
    and secret-store read (cache hits excluded), and for every lifecycle transition.
  - Each record captures the actor (service client, operator, or system), organization, payment
    account, operation, outcome, timestamp, and request correlation id. It never contains the
    value.
  - Audit records are append-only through the service.
  - They can be correlated with the secret store's own access log.
- (R-012) **Rotation.**
  - An account's credentials can be replaced without downtime or failed payments.
  - The new credentials take effect across all instances within the cache lifetime (60 seconds).
  - The previous version remains recoverable for rollback.
  - The last rotation time is tracked per account.
  - Accounts whose credentials exceed a configurable maximum age are reported.
  - The runtime access keys for each environment have a documented rotation procedure with an
    overlap period and a maximum age.
- (R-013) **Secret-store outage handling.**
  - When the secret store is unreachable, throttled, or erroring, any operation that needs
    credentials fails with a distinct, retryable `PROVIDER_CONFIGURATION_UNAVAILABLE` error.
  - It is never reported as `PAYMENT_FAILED`. It creates no failed payment and makes no provider
    call with missing or partial credentials. A retry with the same idempotency key can succeed
    later.
  - Background work that needs credentials, such as webhook verification and event delivery,
    defers and retries instead of discarding work.
  - Permanent misconfiguration is reported as a separate, non-retryable configuration error and
    raises an alert. Examples: access denied, missing secret, malformed payload.
- (R-014) **Caching.**
  - Retrieved credential values may be cached only in process memory, for at most 60 seconds.
  - The cache is bounded in size and never persisted, shared across processes, or logged.
  - It is invalidated immediately in the writing process on store, rotation, or deletion.
  - Cached values are not served beyond their lifetime during an outage. R-013 applies instead.
- (R-015) **Fail-fast configuration.**
  - The service refuses to start if its secret-store configuration is missing, or inconsistent
    with its declared environment. Examples: wrong namespace, wrong encryption key, non-cloud store
    in production.
  - Staging and production can never run with development or test credential stores.
